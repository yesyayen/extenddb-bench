# v0.3 status — implementation log

Tracks decisions made during v0.3 build, especially anywhere we deviated from
the design doc (which is allowed for things the doc didn't pin).

## Locked deviations from `design-v0.3.md`

### D1: Replaced `prometheus-json-exporter` with a tiny in-house shim

**Why.** The design assumed ExtendDB's `/metrics` returns the
"snapshots + histograms" shape with `name`, `dimensions.Operation`,
`buckets/le/count/sum`. The live shape (verified against
ExtendDB SHA `140a1e5e` on 2026-05-26) is:

```json
{
  "metrics": [
    { "metric": "RequestCount",
      "dimensions": [{"Operation": "PutItem"}],
      "window": "Last5Minutes",
      "sum": 1443.0, "count": 1443, "min": 1.0, "max": 1.0 }
  ],
  "buckets": [...],
  "segments": [...],
  "source": "database"
}
```

Three structural mismatches with the design's YAML mapping:

1. Single `metrics` array, not split between counters and histograms.
2. `dimensions` is an array of tagged-enum objects (`[{"Operation": "..."}]`),
   not a flat object with `dimensions.Operation`.
3. **No `le` buckets.** Latency metrics expose `sum/count/min/max` only;
   `percentiles` field is `Option<Percentiles>` and is never populated in
   the `/metrics?window=...` path verified in tree.

`histogram_quantile()` PromQL is therefore impossible against this shape.

The pragmatic shim is a ~120 line Python script
(`infra/lib/user-data/extenddb-metrics-shim.py`) that:

- Pulls `https://127.0.0.1:8000/metrics?window=LastMinute` on each scrape.
- Translates each `MetricSnapshot` into Prometheus exposition lines.
- Emits `_count` (counter from JSON `count`), `_sum_us` (counter from JSON
  `sum`, micros), and `_max_us` (gauge from JSON `max`) per metric/dim
  combo. Mean is derived in PromQL as `_sum_us / _count`.
- Listens on `:9101`, no auth, loopback on the SUT.
- Runs under systemd as `extenddb-metrics-shim.service`.

This keeps the design's intent (Prometheus sees ExtendDB) while swapping
out the off-the-shelf tool for something that fits the actual JSON shape.

### D2: Dashboard PromQL uses derived stats, not `histogram_quantile()`

Direct consequence of D1. The `extenddb-app` dashboard exposes:

- "Request rate by API": `sum by (operation) (rate(extenddb_request_count_count[1m]))`
- "Mean latency by API": `sum by (operation) (rate(extenddb_successful_request_latency_sum_us[1m])) / clamp_min(sum by (operation) (rate(extenddb_successful_request_latency_count[1m])), 1) * 1e-6`
- "Max latency by API (1m)": `max by (operation) (extenddb_successful_request_latency_max_us) * 1e-6`
- p99 latency is unavailable until ExtendDB exposes histogram buckets or
  populates the `percentiles` field. Listed in v0.4 follow-ups.

### D3: Shim emits microseconds, not seconds, in metric names

`extenddb_*_us` makes the unit explicit since the dashboard does the
conversion to seconds in the PromQL (per the design's "pick one place
to do the conversion and document it" rule).

## Scope expansion: flamegraph generation (v0.4-pre)

After the v0.3 acceptance run landed, the user requested flamegraph
generation as a follow-up because the bench's first real demo target,
**PR #122 (feat/auth-cache-pr)**, claims a steady-state catalog-roundtrip
reduction with no perf data attached. RPS / p99 verdicts from
`compare-shas.sh` are necessary but not sufficient to interrogate that
claim; we need to see *where* time goes with vs without the cache.

The original v0.3 design doc explicitly listed flamegraphs as v0.4
backlog under the "don't add features" guardrail. This expansion is a
deliberate scope bump documented here rather than amending the design
doc retroactively. Calling it `v0.4-pre`.

### What the v0.4-pre commits add

| Commit | Adds |
|---|---|
| `4dfe4a8` | sut.sh installs `perf` + `inferno` (Rust port of flamegraph.pl); `kernel.perf_event_paranoid=1`, `kptr_restrict=0` sysctl drop-in; `RUSTFLAGS='-C force-frame-pointers=yes'` baked into both initial cargo build and the swap-sha SSM doc; new SSM docs `extenddb-bench-flamegraph` and `extenddb-bench-apply-config-patch`. |
| `e6e80a1` (or thereabouts) | `scripts/flamegraph.sh` (single-leg capture: drives constant-rps load on the LG, kicks the flamegraph SSM doc on the SUT, syncs SVG + folded stacks back to `results/flamegraphs/<run-id>/<leg>/`). `scripts/apply-config-patch.sh` (managed-block TOML fragment append/clear + restart + health-check). |
| ... | `scripts/compare-flamegraphs.sh` multi-leg orchestrator with `--leg <label>:sha=<sha>[:patch=<file>\|:clear]` syntax, pairwise `inferno-diff-folded` SVGs, markdown report. `--pr-cache` shortcut wires the canonical 3 legs for PR #122. `configs/auth-cache-{off,on}.toml` hold the `[auth.cache]` fragments. |
| ... | `compare-shas.sh --with-flamegraph` opt-in: numerical compare runs first (unaffected), then a 2-leg flamegraph compare on the same SHAs at 80% of the lower achieved RPS. |

### Decisions

- **D6: Frame pointers always-on for bench builds.** `RUSTFLAGS='-C force-frame-pointers=yes'` is unconditional on the SUT, not behind a flag. Aarch64 release builds otherwise omit FPs and `perf record --call-graph fp` would produce broken stacks. The 2-5% steady-state perf cost applies uniformly across every SHA the bench builds, so SHA-vs-SHA comparisons remain fair. Tradeoff: numerical compare results are *not* directly comparable to a deployment that builds without this flag. Documented; mitigated by the fact that this is a perf bench, not a benchmark-the-default-build tool.
- **D7: Profiling is a separate run from numerical compare.** `compare-shas.sh` runs the numerical sweeps first, then optionally a flamegraph leg per SHA. perf record + sleep introduces ~1-3% overhead at 99 Hz; running it during the numerical sweep would taint p99 for that leg. Two sequential phases keep both clean.
- **D8: Diff flamegraphs use inferno-diff-folded.** Pairwise diff across all legs (n*(n-1) SVGs for n legs). Red = hotter on right-hand leg, blue = cooler. The standalone per-leg SVGs are also generated for "long-tail" inspection.
- **D9: Same-SHA different-config legs via apply-config-patch.** New SSM doc edits `/etc/extenddb/extenddb.toml` inside fenced markers (`# >>> bench-managed >>>` / `# <<< bench-managed <<<`), restarts ExtendDB, health-checks. Used to flip `[auth.cache] enabled` on/off without an SHA swap (the cleanest experiment for PR #122).

### Known follow-ups (still v0.4 backlog)

- Differential flamegraph annotations on the bench Grafana dashboard
  (link out to the SVG alongside the leg-tag markers).
- Capturing an off-CPU flamegraph (`perf record --call-graph fp -e sched:sched_switch` + bpftrace) for I/O-bound workloads. Auth-cache changes are CPU-bound on the request fanout, so on-CPU is the right tool here; off-CPU is for v0.4's storage-engine work.
- Caching `perf.data` separately from `perf.folded` -- `perf.data` enables re-rendering with different filters/colorings later, but is large (~50-200 MB per leg). Currently we upload only the folded stacks (~MBs) and the SVG. Add a `--keep-perf-data` flag if needed.
