# v0.3 status — implementation log

Tracks decisions made during v0.3 build, especially anywhere we deviated from
the design doc (which is allowed for things the doc didn't pin).

## Locked deviations from `design-v0.3.md`

### D1: Replaced `prometheus-json-exporter` with a tiny in-house shim

**Why.** The design assumed ExtendDB's `/metrics` returns the
"snapshots + histograms" shape with `name`, `dimensions.Operation`,
`buckets/le/count/sum`. The live shape (verified against
ExtendDB SHA `140a1e5e` on 2026-05-26) is:

```json
{
  "metrics": [
    { "metric": "RequestCount",
      "dimensions": [{"Operation": "PutItem"}],
      "window": "Last5Minutes",
      "sum": 1443.0, "count": 1443, "min": 1.0, "max": 1.0 }
  ],
  "buckets": [...],
  "segments": [...],
  "source": "database"
}
```

Three structural mismatches with the design's YAML mapping:

1. Single `metrics` array, not split between counters and histograms.
2. `dimensions` is an array of tagged-enum objects (`[{"Operation": "..."}]`),
   not a flat object with `dimensions.Operation`.
3. **No `le` buckets.** Latency metrics expose `sum/count/min/max` only;
   `percentiles` field is `Option<Percentiles>` and is never populated in
   the `/metrics?window=...` path verified in tree.

`histogram_quantile()` PromQL is therefore impossible against this shape.

The pragmatic shim is a ~120 line Python script
(`infra/lib/user-data/extenddb-metrics-shim.py`) that:

- Pulls `https://127.0.0.1:8000/metrics?window=LastMinute` on each scrape.
- Translates each `MetricSnapshot` into Prometheus exposition lines.
- Emits `_count` (counter from JSON `count`), `_sum_us` (counter from JSON
  `sum`, micros), and `_max_us` (gauge from JSON `max`) per metric/dim
  combo. Mean is derived in PromQL as `_sum_us / _count`.
- Listens on `:9101`, no auth, loopback on the SUT.
- Runs under systemd as `extenddb-metrics-shim.service`.

This keeps the design's intent (Prometheus sees ExtendDB) while swapping
out the off-the-shelf tool for something that fits the actual JSON shape.

### D2: Dashboard PromQL uses derived stats, not `histogram_quantile()`

Direct consequence of D1. The `extenddb-app` dashboard exposes:

- "Request rate by API": `sum by (operation) (rate(extenddb_request_count_count[1m]))`
- "Mean latency by API": `sum by (operation) (rate(extenddb_successful_request_latency_sum_us[1m])) / clamp_min(sum by (operation) (rate(extenddb_successful_request_latency_count[1m])), 1) * 1e-6`
- "Max latency by API (1m)": `max by (operation) (extenddb_successful_request_latency_max_us) * 1e-6`
- p99 latency is unavailable until ExtendDB exposes histogram buckets or
  populates the `percentiles` field. Listed in v0.4 follow-ups.

### D3: Shim emits microseconds, not seconds, in metric names

`extenddb_*_us` makes the unit explicit since the dashboard does the
conversion to seconds in the PromQL (per the design's "pick one place
to do the conversion and document it" rule).
