# v0.15 status — instrumentation

Adds a third stack (Monitor) running Prometheus + Grafana, plus
`node_exporter` on LG/SUT and `postgres_exporter` on SUT. Three dashboards
auto-provisioned. Compute lifecycle is decoupled from monitor lifecycle so
the dashboard survives `cdk destroy ExtendDbBenchCompute`.

## What changed vs v0.1

| area | change |
|---|---|
| infra | `MonitorStack` added: t4g.medium + 50 GB gp3 EBS (`RemovalPolicy.RETAIN`) |
| infra | `bench` security group opens 9090, 9100, 9187, 3000 intra-SG only |
| infra | LG user-data installs node_exporter and publishes its IP to SSM |
| infra | SUT user-data installs node_exporter + postgres_exporter, enables `pg_stat_statements`, `track_io_timing=on` |
| infra | SSM Parameter Store is no longer CDK-managed — params are populated by user-data and persist across compute redeploys (the monitor reads them) |
| ops | `bench-run` no longer touches the OS trust store; uses `--tls-insecure` (LG-SUT is intra-SG private; SigV4 still authenticates) |
| ops | `scripts/cheatsheet.sh` prints all operator commands for a live stack |
| dashboards | `bench` (loadgen metrics), `hosts` (node_exporter, both instances), `storage` (postgres_exporter + pg_stat_statements) |

## Architecture

```
                ┌─── VPC (us-east-1, single AZ, cluster placement group) ───┐
                │                                                           │
   operator     │   LG (c7g.8xlarge)         SUT (c7g.4xlarge)              │
   laptop       │   ─ extenddb-bench         ─ extenddb (TLS, SigV4)        │
       │        │   ─ :9090 prom (during    ─ postgres 15 (stat_statements) │
       │ SSM    │     sweep only)            ─ :9100 node_exporter          │
       │        │   ─ :9100 node_exporter    ─ :9187 postgres_exporter      │
       │        │                                                           │
       └────────┤   Monitor (t4g.medium, separate stack)                    │
                │   ─ /data on 50 GB gp3 (RETAIN)                           │
                │   ─ Prometheus scrapes bench, node, postgres jobs         │
                │   ─ Grafana on :3000, dashboards auto-provisioned         │
                └───────────────────────────────────────────────────────────┘
```

## Prometheus scrape targets

Discovered via `file_sd_configs` from `/etc/prometheus/targets/{bench,node,postgres}.json`,
which a systemd timer (`refresh-targets.timer`) regenerates every 30 s by
fetching SSM Parameter Store. This means:

- LG/SUT can be torn down and re-deployed without touching the monitor.
- Monitor sees fresh IPs on the next 30 s tick.
- The SSM params survive `cdk destroy ExtendDbBenchCompute` so the targets
  file simply goes empty until LG/SUT come back.

| job | targets | source |
|---|---|---|
| `bench` | `<LG_IP>:9090` | only `up` while a sweep is running |
| `node` | `<LG_IP>:9100`, `<SUT_IP>:9100` | always up once LG/SUT are bootstrapped |
| `postgres` | `<SUT_IP>:9187` | always up once SUT is bootstrapped |
| `prometheus` | `localhost:9090` | self |

## Dashboards

Provisioned via Grafana file-based provisioning (datasource UID
`PBFA97CFB590B2093` baked into the dashboard JSON so they bind cleanly).

- **extenddb-bench live** (uid `bench-live`): target vs achieved RPS,
  latency percentiles from `loadgen_request_duration_seconds_bucket`,
  in-flight, errors by reason, current step / iteration index.
- **extenddb-bench hosts** (uid `bench-hosts`): CPU, load, mem, net, disk
  IO and IOPS for both LG and SUT.
- **extenddb-bench storage (postgres)** (uid `bench-storage`):
  `pg_stat_activity_count` by state, TPS, tuples, block I/O, top 5 mean
  query time from `pg_stat_statements`.

## Lifecycle

```
deploy --all                    # 3 stacks, ~13 min first time
   │
   ├── ExtendDbBenchNetwork     # VPC, NAT, S3 results, bench SG
   ├── ExtendDbBenchMonitor     # t4g.medium + 50 GB EBS RETAIN
   └── ExtendDbBenchCompute     # LG + SUT (depends on Network)

run sweeps repeatedly
   │
   ▼
destroy ExtendDbBenchCompute    # tears down LG + SUT, keeps Monitor live
   │                            # dashboard still works; bench job goes DOWN
   ▼
deploy ExtendDbBenchCompute     # bring LG + SUT back; targets auto-rediscover
   │
   ▼
destroy --all                   # final teardown
   │                            # MonitorDataVolume is RETAINed; you must
   │                            # delete it manually if you want the disk back
   ▼
clean
```

## Known issues / v0.2 line items added during v0.15

- **`refresh-targets` was first written via a bash heredoc with escape
  soup**; rewritten to use `jq` (5/26). Push pending instances pick this up
  on next monitor redeploy.
- **`bench-run` ran as `ssm-user`** but tried to write to
  `/etc/pki/ca-trust/source/anchors/`, which needs root. Removed entirely
  (5/26): `bench-run` now relies on `--tls-insecure`.
- **`MonitorDataVolume` is `RETAIN`** so a stack delete leaves the disk
  attached/orphaned. Acceptable for v0.15 (small cost), needs a
  `cdk destroy --force` flow that snapshots-then-deletes for v0.2.
- **No alerting** in Grafana. v0.2 should add a watchdog rule for the bench
  job going DOWN unexpectedly mid-sweep (i.e. process crash, not normal end).
- **No persisted dashboard edits**. Dashboards are file-provisioned so any
  edit in the UI is wiped on Grafana reload. v0.2 either makes dashboards
  editable + stored on the data volume, or treats them as code only.
- **Compute redeploy still requires `cdk destroy && cdk deploy`** because
  user-data change replaces the SUT instance and the separate
  `CfnVolumeAttachment` doesn't orchestrate detach/reattach cleanly.
